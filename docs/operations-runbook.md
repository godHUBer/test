# Deployment, backup, recovery and incident runbook

**Execution status: not run against the selected project.** The project is `sohan-automobile` / `vxlxoiycolfojcnhnzfr`, previously selected as non-production. Backup readiness was explicitly **not verified**. The phase request does not authorise bypassing this gate or performing a remote reset/import/upload. All steps below that change hosting, DNS, Supabase or data require the relevant owner approval.

## Responsibilities and prerequisites

Before a rehearsal/cutover, privately name a release operator, dealership approver, backup/recovery owner, security contact and on-call/alternate. Record approved recovery-point (RPO) and recovery-time (RTO) objectives; these are business decisions, not numbers this repository invents. Record maintenance window, change/release digest, approved domains, escalation routes and rollback decision deadline. Store passwords/keys/recovery codes in the approved secret manager, never this document, Git, browser fixtures, chat or CI artifacts.

Use Node.js 22+, a supported image-processing runtime for `sharp`, HTTPS and a server that binds `0.0.0.0`. Keep the legacy static source/baseline for parity/recovery, not as the ongoing live database source. Existing six remote migrations must not be replayed or overwritten by the local upgrades.

## Backup and restore readiness — first gate

A provider's enabled backup toggle, successful dump, screenshot, or PGlite fixture is **not** a completed restore exercise.

1. Inventory scope: database schema/data including business/audit/private registry and intake receipts, storage bucket definitions/policies **and actual object bytes**, relevant Auth users/factors/provider configuration, public settings, secrets/configuration references, deployed application version and approved DNS/TLS/Auth redirect settings. Confirm with the provider which parts its backup/export covers; do not assume a database dump includes Storage bytes or all Auth/host settings.
2. Prepare a consistent recovery point. Quiesce writes/intake where necessary or document the consistency method for database rows vs nontransactional Storage. Record cutoff timestamps, schema/migration identifiers, exact row counts by relevant status and media manifests/content hashes. Store artifacts encrypted with restricted access and recovery-key access separate from the backup.
3. Confirm the recovery environment and provider method in advance. Restore **there**, not over the selected existing project as an experiment. Prevent public indexing, real notifications, public media exposure and use of live customers/credentials. For sensitive data, apply the approved isolated access/retention process.
4. Restore actual objects/configuration as well as the database. Verify counts, text IDs, exact rupee prices, null/unknown fields, notes/history/actor links, availability flags, media registry paths/states and byte hashes. Recheck Auth/MFA, bucket/public/private ACLs and RLS grants against effective anonymous/staff/manager/owner calls. Resolve orphaned or partially published media using the Phase 4 runbook.
5. Exercise real sign-in, one draft/photo/publication cycle, one idempotent intake retry and an assigned service/viewing journey. Verify private data remains private after restoration. Measure actual data-loss window and total elapsed recovery time against the approved RPO/RTO.
6. Record redacted evidence, artifact hashes, scope exclusions, failures/retest and reviewer sign-off. Check recovery access without depending solely on the unavailable primary account/device. Remove rehearsal access/data when approved. Only then may `backup_restore` be reviewed as passed.

No automated remote backup/restore command is shipped: the correct provider method, subscription coverage, encryption/storage destination and restore target remain unconfirmed. Do not paste connection strings into shell history or chat to work around this.

## Rehearsal and cutover sequence

1. Freeze a candidate after local CI/security review. Run `npm ci`, `npm run check`, `npm run inventory:dry-run`, `npm run build`, `npm run test:e2e`, `npm audit --omit=dev`, and `npm run release:manifest`. Archive test reports plus candidate identity privately. Do not bundle `.local`, `.generated/test-tls`, `scripts/*fixture*`, `tests`, backups or evidence in a public deployment; fixture/test files are developer tooling only.
2. Reinspect actual schema/grant/storage drift, review all three local upgrade migrations and obtain approval. Rehearse transactional application on the approved isolated environment first; verify markers 2/4/5 and actual effective HTTP/RLS/Auth/Storage behaviour. Direct car/draft-storage/settings write revocations are compatibility changes. No project reset, duplicate parallel schema, automatic legacy import or anonymous customer-table INSERT is acceptable.
3. Reconcile the 15 legacy records against an approved public-column-only export using the offline tool. Differences may reflect legitimate newer business edits; review them instead of forcing equality. Separately verify all real media objects/paths, price semantics, optional/null values and current dealership-confirmed availability. No importer or automatic overwrite/publish is authorised by a matching comparison report.
4. Execute [real staff acceptance](staff-acceptance.md), native concurrent-session tests, failover/timeouts and manual accessibility/device testing. Fix critical findings and retest before proceeding.
5. Deploy the reviewed build to an isolated real HTTPS rehearsal host. Configure publishable values at build/runtime as appropriate and service credentials only in the server secret store. Verify no secret appears in frontend bundles, error/log collectors or browser props. `NEXT_PUBLIC_*` values may be embedded at build time: runtime edits alone do not reliably change those artifacts.
6. Verify canonical `SITE_URL`, public/staff/project URL consistency, Auth Site URL/redirect allowlist/email templates, SMTP eligibility/throttling, first-owner recovery/TOTP procedures, private cache behaviour, Origin/forwarded-host handling and browser-accessible relative paths. Browser code must not call `localhost` for services. Trusted-network headers require a verified overwriting proxy and blocked direct-origin bypass.
7. Apply deployment-specific protections: edge rate/WAF limits, body/resource ceilings, request timeouts, concurrency capacity and monitoring. Current application CSP protects `base-uri`/`object-src` only; it is **not a complete script or clickjacking policy**. Rehearse a nonce/hash-compatible script policy and an explicit `frame-ancestors` allowlist at the deployment edge, retaining any approved preview embeds. Do not blindly add `X-Frame-Options: DENY` to Arena's embedded preview. Enable HSTS only for the approved HTTPS domain after TLS/subdomain/rollback review; do not preload/includeSubDomains casually. Verify ingress doesn't override private no-store/referrer controls.
8. Sign off legal/retention/contact/service details and staffing to manually review the queue; automatic lead notifications remain disabled. Keep `BUSINESS_INTAKE_ENABLED=false` before customer-intake approval. An operational incident should show a real unavailable/contact message, not republish historical snapshot cars as current live stock.
9. In the **approved target environment with securely injected variables**, run `npm run release:check -- --evidence .local/release/evidence.json`. It reads the process environment, not Next's `.env.local` automatically. Only the owner/operator can approve deployment after reviewing the evidence; a machine `REVIEWED_CANDIDATE` result is not itself authorisation.
10. After explicit cutover approval, make the planned remote/config/DNS changes during the agreed window, run real smoke checks and monitor. Record the actual deployment artifact identifier/hash and first successful provider/staff checks separately from the source digest. Keep writes and legacy snapshot visibility controlled throughout. **These steps have not been executed.**

## Daily operation / monitoring

- Assigned staff review their lead/service queue and due follow-ups; managers review unassigned/new requests and affected bookings after stock changes. No email/SMS alert is implied by saving a record. Dashboard values are permission-scoped counts, not revenue.
- Monitor public availability/detail/robots checks, staff sign-in/provider health, aggregate intake failures/limit rejections, stale/conflict errors, Storage/processing failures, queue ageing/unassigned load and recovery-backup freshness. Synthetic probes must use dedicated test records and approved rate budgets, not real customer submission spam. Dynamic public pages use fresh database reads; do not treat a provider error as empty stock or serve stale availability from an arbitrary CDN cache.
- Name actual alert destinations and test delivery. This repository does not configure a monitoring vendor or claim alerts are live. Never log form bodies, contacts/messages/notes, auth tokens, cookies, service keys, signed URLs, QR codes or full provider response payloads. Sanitise query strings/referrers in ingress/APM as well as app logs. Use opaque event IDs, counts, status classes and timestamps where possible.
- Periodically repeat real restores, staff access review, provider/dependency updates, frontend secret scan and manual keyboard/screen-reader/device smoke checks. Retain reports only under the approved policy. Current application logs are append-only for app roles, not an immutable external ledger or a complete authentication-read log.

## Incident / rollback decision table

| Incident | Immediate safe action | Reconcile before resuming |
| --- | --- | --- |
| Suspected private-data/credential exposure | Restrict relevant routes at ingress, disable intake where needed, revoke exposed server key/session using the approved provider process; notify named owner/security contact | Scope/log access, credential rotation across replicas, storage exposure, affected people/legal obligations and preserved evidence. Removing a public URL does not retract already downloaded bytes |
| Intake uncertain / duplicate report | Do not promise success or ask the customer to keep reloading new forms; keep manual phone/email route | Authorised staff search by supplied reference/contact in a controlled process; compare receipt/request/job counts. Preserve unchanged retries/signing secret while reconciling; do not bulk-delete leads |
| Public inventory/provider outage | Show unavailable state or a clearly non-operational maintenance/contact page; disable unsafe writes | Provider health, configuration/schema markers and actual availability. **Do not switch a live dealership to the old unverified snapshot as if it were current stock** |
| Ambiguous photo upload/publication | Stop repeat public publication/deletion attempts | Compare private/public bytes and registry state under the reviewed Phase 4 reconciliation process. Preserve audit/actor evidence |
| Bad application release, compatible schema | Stop ingress writes/intake and route to approved maintenance; revert only to a tested compatible application artifact | Ensure previous code respects current grants/contracts and displays honest states. Recheck reads/Auth/provider before resuming writes |
| Corrupt data or incompatible schema | Freeze writes, preserve incident snapshot/logs; involve recovery owner | Restore into recovery environment first, reconcile data/media/receipts and post-cutoff writes, approve recovery point/loss before any live replacement. Never blindly run reverse/drop migrations or reset the project |

An application rollback is not a database/media rollback. Do not undo migrations by deleting new tables/receipts or discard legitimate post-cutover leads. Save an incident timeline (UTC with optional IST display), affected release/configuration identifiers, actions/approvals and a handover. After recovery, repeat privacy/RLS, idempotency, photo/public stock and staff acceptance checks; record actual restored RPO/RTO and a post-incident review.

## Deferred features / launch-scope decisions

Owner-authorised CSV exports (with recent MFA, safe cell encoding and an audited preparation event), automatic retention/purge, custom photo alt-text editing, detailed upload telemetry, consolidated calendar/shift/business-hour rules and automatic notifications remain unimplemented. The launch approver must explicitly accept or commission them; the original export proposal is not silently marked delivered. There is no assumed full workshop ERP or customer-document upload. Neither this runbook nor a green local suite waives these scope decisions or any critical launch issue.
